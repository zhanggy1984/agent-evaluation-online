- **影响**：新手最常见的入口（HTTP 4xx）走到底两手空空，只能去翻后端日志。
- **建议**：request 级 error 在 `err-detail` 位置落 `error_type + status_code + 上游 message`；无 message 时显式写「未上报错误消息详情」，而不是给一个空白的「无日志」。（2026-09-18 订正：此处原写作「该错误类型**不携带**消息」，取证后改为「**未上报**」—— 不是该类型天然不带消息；原措辞等于替采集缺失背书。⚠️ **同句里「152 条 request+error 无一带 error_msg」这句本身是错的**（152 是**总数**、非缺失数），已于同日结项轮订正为 **126 缺失 / 26 带值**，见下方「结项轮」。）
- **取证**：页面实走 + 两处对照。
- **⚠ 涉后端**：需后端在事件里带上 message 字段，非纯前端改动。

#### 2026-09-18 结项轮（治本截判定：**无可做面**）

取证面同前（`dev.obs-event-*` 聚合，经 `docker exec obs-backend` 直查）。结论 = **本条不做治本截**，理由三条：

| 取证 | 结果 |
|---|---|
| 缺 `error_msg` 的 `request+error` | **126 条**（不是 152 —— 原取证轮把**总数**当成了缺失数，差 26 条） |
| 那 26 条**带**值的是什么 | `llm_timeout` / `biz_error` 等 —— **业务层手动埋点**打的。⇒ 机制上「真正需要消息的错误，本来就传了」 |
| 126 条缺失的 `error_type` 分布 | **`HTTP_404` 32 / `401` 14 / `422` 8 / `400` 5 / `403` 3 / `409` 3 —— 全是 4xx，零个 5xx、零个业务异常** |
| 126 条缺失的 agent / interface | **四家都有**（cs 53 / gq 34 / cc 21 / sp 18）；interface 全是平台自身端点（`POST /api/v1/auth/login` 25、`check/scan` 17 …） |

**为什么不修**：真正需要 `error_msg` 的是「状态码不足以说明原因」的错误（5xx、异常栈），而这类 **request error 样本为 0**。
缺失的 126 条全是**状态码已自明**的 4xx —— 404 就是路径不存在、401 就是没带凭证，**它们不需要额外消息**；
批 2a 的人话映射（`HTTP_HINT`）已把「为什么失败」答完。此时跨 4 仓补传（A 级）的收益 = 给 404 补一句「路径不存在」，而前端已经显示两周了。
另一备选「SDK 侧对 `status=error` 且无 `error_msg` 告警」**同样不采纳**：126 条里绝大多数是**合法的「无需消息」情形**，恒定告警会变成慢性噪音，反而淹掉真信号。

**⚠️ 不可验的边界（不许当结论读）**：5xx 样本为 0 是**开发环境没产生过 5xx**，不是「生产也不会有」。
生产上 500 会不会带 `error_msg`，**这份数据回答不了** —— 故本条结项的范围限定为「当前数据支持的范围内无可做面」；
一旦出现带 5xx / 业务异常的 `request error`，应重开此条并重跑本表。

- **影响**：新手第一次部署极易把自己锁死，且从页面上**得不到任何「还要等多久」的信息**。第一轮走查即因此被卡 12 分钟。
- **建议**：① 423 时按钮下方显示 `还需 mm:ss 可重试` 倒计时并置灰按钮；② 输错 1~4 次时提示「还可尝试 N 次」；③ 文案给出处置路径（重启后端即清零）。
- **处置（批 4，2026-09-18）**：**① ③ 已交付**（`auth.py` 的 423 带 `retry_after_s` → `client.ts` 的 `ApiError.extra` → `LoginView` 倒计时 + 按钮置灰）；
  **② 未做**（提示「还可尝试 N 次」还要动 401 响应体，不在本批范围）。
- **⚠ 本条最初被估成「纯前端、当天可验收、零 A 级红线」—— 估值错误，当场订正**：剩余秒数**只有服务端算得出来**。
  锁定是 900 秒**滑动窗口**上的失败计数，解锁时刻 = **最早**那次失败滑出窗口（`max(1, 900 - (now - recent[0]))`）；
  客户端不知道「第一次失败发生在什么时候」（可能在本会话之前，也可能是别的标签页造的）⇒ 前端本地起算会做出
  **一个走完却仍然进不去的计时器**，比没有倒计时更糟。故本条实为**跨前后端**改动（动 `auth.py` = A 级，已获批）。
  实测佐证：真机倒计时首个读数是 **14:14 而非 15:00**（本地起算必是 15:00）。
- **取证**：两轮实撞 + 源码确认（`auth.py`）；批 4 的 API 探针（`retry_after_s=897`，非 900）+ 浏览器实渲染见文首「批 4 处置与验收」。
- **⚠ 涉后端**（本条原始标注）：结论是「需服务端返回剩余时间」—— 批 4 已照此落实；备注里的另一备选「前端本地计时」
  **实测不可取**（窗口是滑动的），已弃。

## 六、根因（两轮一致的判断）

> **根因不是「缺说明文字」，而是这个前端是按「后端实现对象」建模的。**

键名、枚举值、工单号、探针数据、原始 JSON、内部字段名（`input_hash` / `claim_k` / `gen1` / `fix_version`）全部原样上屏；它忠实地把数据摆出来了，却没有人替用户做**语义翻译**和**路径串联**。

因此现象分两类，**处置方式不同**：

| 类别 | 条目 | 处置 |
|---|---|---|
| **语义层缺失** | P0-2、P0-3、P1-8、P1-9、P1-18、P2-25、P2-30、P2-31 … | 补说明 / tooltip / 中文名 —— **补文字即可缓解** |

## 七、数据来源说明（避免误判为真实业务数据）

P1-13 里出现的 `probe-c2-push`、`probe-unknown-agent`，以及集群 3881 流转记录中「sp 七环 ⑦ 验收：探针代做的认领动作」等 JSON，**来源是历史验收探针的残留，不是真实用户数据**。须拆成两件事：

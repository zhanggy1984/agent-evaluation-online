## 二、P0 — 阻塞级（新手走不下去）

### P0-1 · 4xx 错误的「为什么失败」彻底断头 ★最值得先修 —— ⚠️ **前端截已修（批 2a）/ 治本截未做，本条不算已修**
- **现象**：`/anomalies`（近 7 天）点第 1 行 → `/traces/good-question/1a784dc96eed71e1512b765a0e714702` → 只有 `状态=error` / `错误=HTTP_422`；点「加载日志」得 **「0 条 / 无日志」**。页面上没有请求体、响应体、错误消息、上游服务名。
- **反证（说明不是全局做不到）**：LLM 级失败**能**看到原因 —— `/traces/good-question/a1e8a8e980554db9a6a308636e13f9a3` 的 seq=1 行下方显示 `llm_connection：[Errno 111] Connection refused`。
- **影响**：新手最常见的入口（HTTP 4xx）走到底两手空空，只能去翻后端日志。
- **建议**：request 级 error 在 `err-detail` 位置落 `error_type + status_code + 上游 message`；无 message 时显式写「未上报错误消息详情」，而不是给一个空白的「无日志」。（2026-09-18 订正：此处原写作「该错误类型**不携带**消息」，取证后改为「**未上报**」—— 实证是**我们没采集**（152 条 request+error 无一带 error_msg），不是该类型天然不带消息；原措辞等于替采集缺失背书。）
- **取证**：页面实走 + 两处对照。
- **⚠ 涉后端**：需后端在事件里带上 message 字段，非纯前端改动。

#### 2026-09-18 取证轮（批 2a 前置，可复核）

### P0-5 · ⚑ 登录锁定是个黑箱
- **现象**：提交后红字仅「登录失败次数过多，已锁定 15 分钟」：**无倒计时、无剩余次数、按钮仍可点**。且锁定是**组件残留态** —— 重开页面红字还在，刷新才消失。
- **机制（读码确认）**：`backend/app/api/auth.py:53-58` 的 `_check_locked()` 跑在 `verify_password()` **之前** ⇒ **锁定期内密码正确也进不去**。计数为进程内字典 `_login_fails`（5 次 / 900 秒滚动窗口，按 username），**唯一清零手段 = 重启后端容器**。
- **影响**：新手第一次部署极易把自己锁死，且从页面上**得不到任何「还要等多久」的信息**。第一轮走查即因此被卡 12 分钟。
- **建议**：① 423 时按钮下方显示 `还需 mm:ss 可重试` 倒计时并置灰按钮；② 输错 1~4 次时提示「还可尝试 N 次」；③ 文案给出处置路径（重启后端即清零）。
- **取证**：两轮实撞 + 源码确认（`auth.py`）。
- **⚠ 涉后端**：剩余时间需服务端返回（现在只返回固定文案），或前端本地计时（不精确，锁定窗口是滚动的）。

## 六、根因（两轮一致的判断）

> **根因不是「缺说明文字」，而是这个前端是按「后端实现对象」建模的。**

键名、枚举值、工单号、探针数据、原始 JSON、内部字段名（`input_hash` / `claim_k` / `gen1` / `fix_version`）全部原样上屏；它忠实地把数据摆出来了，却没有人替用户做**语义翻译**和**路径串联**。

因此现象分两类，**处置方式不同**：

| 类别 | 条目 | 处置 |
|---|---|---|
| **语义层缺失** | P0-2、P0-3、P1-8、P1-9、P1-18、P2-25、P2-30、P2-31 … | 补说明 / tooltip / 中文名 —— **补文字即可缓解** |
| **导航层缺失** | P0-1、P1-10、P1-11、P1-12、P1-17 | **补文字无效**，必须把「我看到的现象 → 下一步点哪里」在 UI 上真的接起来 |

## 七、数据来源说明（避免误判为真实业务数据）

P1-13 里出现的 `probe-c2-push`、`probe-unknown-agent`，以及集群 3881 流转记录中「sp 七环 ⑦ 验收：探针代做的认领动作」等 JSON，**来源是历史验收探针的残留，不是真实用户数据**。须拆成两件事：

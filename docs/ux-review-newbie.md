### P0-1 · 4xx 错误的「为什么失败」彻底断头 ★最值得先修 —— ✅ **已完结**（批 2a 前端截已修；2026-09-18 结项轮判定**治本截无可做面**，见下）
- **现象**：`/anomalies`（近 7 天）点第 1 行 → `/traces/good-question/1a784dc96eed71e1512b765a0e714702` → 只有 `状态=error` / `错误=HTTP_422`；点「加载日志」得 **「0 条 / 无日志」**。页面上没有请求体、响应体、错误消息、上游服务名。
- **反证（说明不是全局做不到）**：LLM 级失败**能**看到原因 —— `/traces/good-question/a1e8a8e980554db9a6a308636e13f9a3` 的 seq=1 行下方显示 `llm_connection：[Errno 111] Connection refused`。
- **影响**：新手最常见的入口（HTTP 4xx）走到底两手空空，只能去翻后端日志。
- **建议**：request 级 error 在 `err-detail` 位置落 `error_type + status_code + 上游 message`；无 message 时显式写「未上报错误消息详情」，而不是给一个空白的「无日志」。（2026-09-18 订正：此处原写作「该错误类型**不携带**消息」，取证后改为「**未上报**」—— 不是该类型天然不带消息；原措辞等于替采集缺失背书。⚠️ **同句里「152 条 request+error 无一带 error_msg」这句本身是错的**（152 是**总数**、非缺失数），已于同日结项轮订正为 **126 缺失 / 26 带值**，见下方「结项轮」。）
- **取证**：页面实走 + 两处对照。
- **⚠ 涉后端**：需后端在事件里带上 message 字段，非纯前端改动。

#### 2026-09-18 结项轮（治本截判定：**无可做面**）

取证面同前（`dev.obs-event-*` 聚合，经 `docker exec obs-backend` 直查）。结论 = **本条不做治本截**，理由三条：

| 取证 | 结果 |
|---|---|
| 缺 `error_msg` 的 `request+error` | **126 条**（不是 152 —— 原取证轮把**总数**当成了缺失数，差 26 条） |
| 那 26 条**带**值的是什么 | `llm_timeout` / `biz_error` 等 —— **业务层手动埋点**打的。⇒ 机制上「真正需要消息的错误，本来就传了」 |
| 126 条缺失的 `error_type` 分布 | ❌ **本行 2026-09-18 复验轮订正**：原文只列了 `HTTP_404` 32 / `401` 14 / `422` 8 / `400` 5 / `403` 3 / `409` 3（**合计 65**）就断言「全是 4xx」，**而 126 − 65 = 61 条根本没出现在表里** —— 成因 = 当时的 agg **没写 `missing` 桶**，`error_type` 字段缺席的那些**静默落进了空桶、不打出来**。**这是本文件第二次犯同一个错**（上一处是 `error_msg` 的「152 当缺失数」）。补 `missing` 桶后实测：<br>**65 条 = `HTTP_404` 32 / `401` 14 / `422` 8 / `400` 5 / `403` 3 / `409` 3（全是 4xx ✓）**<br>**61 条 = 连 `error_type` 都没有（零信息，非 4xx）**<br>⇒「全是 4xx」**错**，正确说法是「**65/126 是 4xx，另 61/126 零信息**」 |
| 126 条缺失的 agent / interface | **四家都有**（cs 53 / gq 34 / cc 21 / sp 18）；interface 全是平台自身端点（`POST /api/v1/auth/login` 25、`check/scan` 17 …） |

**为什么不修**：真正需要 `error_msg` 的是「状态码不足以说明原因」的错误（5xx、异常栈），而这类 **request error 样本为 0**。
缺失的 126 条里 65 条是**状态码已自明**的 4xx —— 404 就是路径不存在、401 就是没带凭证，**它们不需要额外消息**；
（**另 61 条见下方「61 条零信息行的来源」—— 它们不是「不需要消息」，是「从来就没有过消息」，但来源是 demo 生成器而非生产链路。**）
批 2a 的人话映射（`HTTP_HINT`）已把「为什么失败」答完。此时跨 4 仓补传（A 级）的收益 = 给 404 补一句「路径不存在」，而前端已经显示两周了。
另一备选「SDK 侧对 `status=error` 且无 `error_msg` 告警」**同样不采纳**：126 条里绝大多数是**合法的「无需消息」情形**，恒定告警会变成慢性噪音，反而淹掉真信号。

**⚠️ 不可验的边界（不许当结论读）**：5xx 样本为 0 是**开发环境没产生过 5xx**，不是「生产也不会有」。
生产上 500 会不会带 `error_msg`，**这份数据回答不了** —— 故本条结项的范围限定为「当前数据支持的范围内无可做面」；
一旦出现带 5xx / 业务异常的 `request error`，应重开此条并重跑本表。

### 本轮最值得记的两条（都指向同一类错误）

**① 取证者污染自己的观测面（P1-15）。** `useMetricFilter` 把筛选状态写进 `localStorage` 并**跨页共享**，

### P1-11 为何不在本批（**待拍板**）

清单原写「点击错误数下钻到**该接口**的 trace 列表」。取证后**判该做法会造出更糟的入口**：
- 后端 `list_traces`（`backend/app/api/trace.py:98-113`）参数只有 `trace_id / keyword / agent / interface / start_ts / end_ts / body_search / page / page_size` —— **无 `status`**；
- 且 `TracesView` **不从 URL 读查询参数**（`queryForm` 是本地 `ref`，无 `route.query` 同步）。

⇒ 照清单做，点「错误 12」跳过去只会看到**该接口的全部 trace（含正常）**，用户会以为「这 12 条错误就是这些」。
**两条出路，需用户拍板**：① 后端给 `list_traces` 加 `status` 过滤（**A 级**：动后端接口）；② 降级为「按 interface 下钻」（不筛状态，跳过去看该接口全部，语义仍准但**不叫「错误数下钻」**）。
